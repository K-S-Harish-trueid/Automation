STEP 2 -- replace ("Historical Override")
================================================================================
TYPE      auto (fully automatic, no operator gate)
CODE      backend/app/pipeline/stages/replace.py :: stage_replace_from_sql,
          stage_replace_reference, validate_replace_reference_inputs,
          REPLACE_MAPPING_COLS
          backend/app/historical_db.py :: has_data, load_reference_df

WHAT IT DOES
Runs automatically during the auto-stage chain (same as Initial Data
Cleaning) -- overwrites the current dataset for any account matched on
ACCOUNT_NUMBER, using values pulled straight from the historical SQL
store (SQLite, backend/data/historical.db) instead of an uploaded file.
No operator action, no pause.

CONSTRAINTS -- stage RAISES (fails the job with a visible error) if
  1. The historical SQL store hasn't been seeded yet (historical_db.has_data()
     is False). Fails loudly rather than silently shipping a job with no
     override applied.

MATCHING RULES
  1. Match key: ACCOUNT_NUMBER, compared as a whitespace-trimmed string on
     both sides -- not a numeric comparison.
  2. If ACCOUNT_NUMBER repeats in the historical store, rows are sorted by
     ACCOUNT_NUMBER and only the LAST occurrence of each duplicate is kept
     (this is enforced when data is written into the store, via
     seed_from_file/upsert_rows -- the store itself has a UNIQUE index on
     ACCOUNT_NUMBER so it can never hold true duplicates).
  3. Accounts present in the base dataset but absent from the historical
     store are left completely unchanged.

FIELDS OVERWRITTEN FOR MATCHED ACCOUNTS (REPLACE_MAPPING_COLS)
ACCOUNT_LAST_NAME, ACCOUNT_FIRST_NAME, ACCOUNT_MIDDLE_NAME, DATE_OPENED,
ACCOUNT_HOLDER_DOB, ACCOUNT_TYPE, CARD_TYPE, ACCOUNT_ADDRESS, ADDRESS_CITY,
ADDRESS_PROVINCE, ADDRESS_COUNTRY, POSTAL_CODE, PHONE_NUMBER, EMAIL_ADDRESS,
ID_TYPE, ID_NUMBER, ID_COUNTRY, NATIONALITY, ISSUING_FI, CARD_PROGRAM,
CARD_STATUS, SECONDARY_CARD_TYPE.

FIELD EXPLICITLY NEVER TOUCHED HERE
CARD_NUMBER -- never overwritten by this step, even for matched accounts.

KEEPING THE HISTORICAL STORE CURRENT
- One-time/occasional full reseed from a fresh export:
  historical_db.seed_from_file(path) -- replaces the whole table.
- Ongoing growth: historical_db.upsert_rows(df), wired to the "Update
  historical data" button on the Stage 3 done screen -- inserts or
  replaces (by ACCOUNT_NUMBER) a completed job's own rows into the store,
  so future jobs' Historical Override picks up what this job resolved.
  Safe to call repeatedly, never duplicates.

HISTORY
Was previously an "upload" gate (operator supplied a file each job, or
later a "Use from SQL" button); moved to fully automatic once the SQL
store existed and reuploading a file every job stopped being necessary.
See DONE for the full change log.
