STEP 10 -- default_id ("Default ID Assignment")
================================================================================
TYPE      confirm (requires explicit operator confirmation, no editing)
CODE      backend/app/pipeline/stages/default_id.py :: stage_default_id_assign,
          default_id_invalid_mask

WHAT IT DOES
Guarantees every row leaves the pipeline with a valid ID, by generating one
for whatever the operator did not (or could not) fix manually at step 9.

SCOPE
Applies to every row that still fails the same ID_TYPE/ID_NUMBER validity
check used in steps 5 and 9 (compute_id_validity), evaluated after step 9
has finished.

CONSTRAINTS
  1. PREVIEW FIRST -- before running, GET /jobs/{id}/current for this
     stage returns affected_count, so the operator sees the impact before
     confirming.
  2. UNIQUENESS -- build a set of every ID_NUMBER value already present
     anywhere in the dataset, including on rows still invalid, to
     guarantee no collisions with existing data.
  3. GENERATION -- for each affected row, generate a candidate ID
     formatted as "00" + 6 random digits (pattern 00######, always 8
     characters). Re-roll if the candidate is already in the used set
     (own newly generated IDs included), so every generated ID is unique
     across the whole dataset.
  4. ASSIGNMENT -- set ID_NUMBER to the generated value and ID_TYPE to
     "Civil Id" for every affected row. No other fields are touched.

EDITABLE FIELDS
None -- this step assigns, it doesn't accept operator edits.

ADVANCE RULE
Only runs after an explicit POST /jobs/{id}/confirm call; there is no
skip -- every row still invalid at this point WILL receive a generated ID
before the job can reach "done".
