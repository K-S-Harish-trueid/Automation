STEP 5 -- id_dob_validate ("Missing ID & DoB")
================================================================================
TYPE      manual_edit (pages 200 flagged rows at a time)
CODE      backend/app/pipeline/stages/id_dob_validate.py :: compute_dob_validity,
          mask_id_dob_invalid, validation_reasons_id_dob
          backend/app/pipeline/toolbox.py :: compute_id_validity, id_reason_checks,
          series_available, parse_dob_series (shared with final_id_check/default_id)

WHAT IT DOES
A row passes only if it clears ALL THREE checks below: ID type valid, AND
ID number valid for that type, AND DOB valid. Anything else is flagged.

DEFINITION -- "available"
Not blank after trimming, and not one of the placeholder values (checked
case-insensitively): "", "0", "00000", "null", "none", "na", "n/a",
"xxx_not_collected_xxx".

CHECK 1 -- ID_TYPE
  1. ID_TYPE must be available (see definition above); otherwise invalid.
  2. If ID_TYPE (case-insensitive) == "doc" -> ALWAYS INVALID.
     -> reason: "ID type 'doc' is not accepted. Use Passport, National Id,
        or Civil Id."
  3. Accepted values (case-insensitive), anything else is invalid:
       "passport"
       "national id" / "nid" / "nationalid"
       "civil id" / "civilid" / "civil_id"
     -> reason (for blank or unrecognized, non-"doc" values): "ID type
        must be Passport, National Id, or Civil Id."

CHECK 2 -- ID_NUMBER (only meaningful once ID_TYPE is one of the three
accepted types; never checked for "doc" or an unrecognized type)
  1. Passport -> ID_NUMBER must fullmatch [A-Za-z][A-Za-z0-9]{7,8} (one
     letter followed by 7-8 more letters/digits = 8-9 characters total,
     first character must be a letter).
     -> reason: "Passport number must contain 8-9 alphanumeric characters
        and start with a letter."
  2. National Id -> ID_NUMBER must fullmatch \d{12} (exactly 12 digits, no
     letters, no separators).
     -> reason: "National ID must contain exactly 12 digits."
  3. Civil Id -> ID_NUMBER just needs to be "available" (see definition
     above) -- no format/length check at all.
     -> reason if missing: "Civil ID number is required."
  4. Any accepted type -> an ID_NUMBER made only of zeros (e.g.
     "000000000000", "00000000") is INVALID. Zeros inside a real number
     (e.g. "100200300") are fine.
     -> reason: "ID number cannot be all zeros."
  5. If ID_TYPE itself is invalid/unrecognized, ID_NUMBER is reported as
     unverifiable.
     -> reason: "ID number cannot be validated until a valid ID type is
        selected."

CHECK 3 -- DATE OF BIRTH (ACCOUNT_HOLDER_DOB)
  1. Must be available (see definition above).
     -> reason if not: "DOB is missing."
  2. Must parse as a real date -- tries the exact format
     "%Y-%m-%d %H:%M:%S" first, then a bare "%Y-%m-%d" (parsed literally,
     no day-first inference -- year-month-day order is already unambiguous),
     then a flexible day-first parse as the last resort for anything else
     (e.g. DD/MM/YYYY-style values).
     -> reason if none succeed: "DOB is not a recognized date."
  3. Parsed date must be strictly after 1 January 1905 (1905-01-01 itself or
     earlier is treated as a placeholder/default date).
     -> reason: "DOB must be after 1 January 1905."
  4. Parsed date must not be in the future.
     -> reason: "DOB is in the future."
  5. (Only checked once the DOB itself passes checks 1-4 above -- a broken
     DOB doesn't also spawn a nonsensical age/opening-date reason derived
     from it.)
     a. DATE_OPENED, if it parses, must not be in the future. Independent of
        the age checks below -- both can be true and both get reported.
        -> reason: "Account opening date is in the future."
     b. Two independent age checks, exact calendar age (not a days/365.25
        approximation):
        i.  Currently (as of today) >= 18 years old.
            -> reason: "Customer is currently under 18."
        ii. SWITCHED OFF (Nov 2026, management decision) -- was: >= 18
            years old as of DATE_OPENED. Customers who were minors when the
            account was opened now keep their DOB. Commented out in
            compute_dob_validity / _dob_reason_checks, not deleted.
            -> reason (not used now): "Customer was under 18 when the
               account was opened."

EDITABLE FIELDS
ID_TYPE, ID_NUMBER, ACCOUNT_HOLDER_DOB.

CONTEXT COLUMNS SHOWN (read-only)
ACCOUNT_NUMBER, ACCOUNT_FIRST_NAME, ACCOUNT_LAST_NAME.

ADVANCE RULE
Re-validates after every batch. Advances once zero rows remain flagged, or
immediately on force_advance=true. Rows still ID-invalid when this step is
skipped are picked up again at step 9 (final_id_check). The DOB check is
repeated at the Stage 3 Haider merge -- see "DOB AT STAGE 3" below.

DOB AT STAGE 3 (Haider's corrected file)
CODE      backend/app/pipeline/stage_merge.py :: _validate_haider_dob_sheet,
          apply_haider_corrections_response, apply_cms_card_response
          backend/app/routes/handoff.py :: _sent_accounts
Only Haider's DOB sheet is checked at Stage 3 -- rows that were never sent
to him already passed Stages 1-2 and are kept exactly as they are.
  1. NOT SENT -- kept as is, no check.
  2. SENT, HAIDER GAVE A VALUE -- his value is checked with the DOB rules
     above EXCEPT the 1905 cutoff (rule 3): a pre-1905 DOB from Haider is
     accepted. Valid -> merged. Blank or invalid (not a real date, in the
     future, under 18 today, opening date in the future) ->
     XXX_NOT_COLLECTED_XXX. (mask_dob_invalid(df, check_cutoff=False).)
  3. SENT, NOT RETURNED -- any account in the DOB Corrections sheet sent to
     Haider (frozen stage2_haider.xlsx) but missing from his response ->
     XXX_NOT_COLLECTED_XXX, whatever the reason it was sent (pre-1905
     included).
  4. A row Haider returns that wasn't sent is checked the same way as 2.
Audit: Haider's real DOB corrections are labelled "Haider corrected"; DOBs
set to the placeholder in 2/3 are labelled "Not collected".
Stages 1-2 still flag a pre-1905 DOB, so it is still sent to Naresh/Haider.

NAMES AND IDS AT STAGE 3 (Haider's corrected file)
CODE      backend/app/pipeline/stage_merge.py :: _fill_sent_blanks,
          apply_haider_corrections_response
          backend/app/routes/handoff.py :: _sent_accounts
Only accounts in the Name Validation / ID Corrections sheets of the frozen
stage2_haider.xlsx are affected. Rows never sent are kept as they are.
  1. NAMES -- his values are used. Any of the 3 names left blank, or the
     row not sent back -> ALL 3 (first, middle, last) set to
     XXX_NOT_COLLECTED_XXX.
  2. IDS -- his values are used, NO format check. ID_TYPE or ID_NUMBER
     blank, or the row not sent back -> BOTH set to XXX_NOT_COLLECTED_XXX.
  3. A row Haider returns that wasn't sent keeps the old rule: blank =
     keep the current value.
Audit: real corrections are labelled "Haider corrected"; values set to the
placeholder are labelled "Not collected" (operator System).

CMS DATE_OPENED IN THE FUTURE (Stage 3, CMS Card Details)
A DATE_OPENED from the CMS card file that is in the future is applied as
received (not blocked). It is counted in the Stage 3 summary as a warning
and its audit entry is labelled "CMS warning".
